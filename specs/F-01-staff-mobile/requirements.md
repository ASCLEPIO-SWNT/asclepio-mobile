# F-01-staff-mobile — Acceso del personal y sesión por principal

Brief global: `../asclepio-api/docs/product/features/F-01.md` (F-01.AC1–AC4, AC7–AC8); ampliación móvil autorizada: `docs/mobile-migration.md`, bloque F-01-staff-mobile y reglas transversales.
Contrato: consume **0.4.0**, con F-01-api terminado. API, web y legacy son solo lectura.
RNF aplicables: RNF-05, RNF-10, RNF-11, RNF-12, RNF-13, RNF-14, RNF-18.
Aprobación: el usuario solicitó **«PLEASE IMPLEMENT THIS PLAN»** el 2026-10-29 (America/Bogota) para el plan móvil completo. Esta spec materializa ese alcance antes del código; `docs/adr/0002-pacientes-y-personal.md` registra su ampliación del cliente. No se atribuye a F-01.AC6, redactado para web, un criterio móvil inexistente.

Glosario: **principal verificado** = respuesta válida de `/me` PATIENT del tenant recordado o STAFF con uno de los cuatro roles publicados; **generación** = identidad local de un intento/sesión, invalidada al cerrar/cambiar acceso; **datos privados** = identidad personal, credenciales, listas, formularios y clínica; **destinos** = matriz de `design.md`, con marcadores pendientes para funciones de bloques posteriores. Las pruebas Kotlin se nombran `R<n> ` con espacio, sin dos puntos.

## Requisitos

- **R1** (Ubicuo) El sistema deberá ofrecer en una sola APK entradas separadas Paciente y Personal, conservar selección de IPS/sede, alta con consentimiento y login por documento del paciente, y ofrecer para personal únicamente login por correo y contraseña, sin registro público de personal. (→ F-01.AC1, F-01.AC7, F-01.AC8; plan móvil, bloque F-01-staff-mobile)
- **R2** (No deseado) Si el formulario de personal tiene correo vacío o sin formato de correo, o contraseña vacía o de más de 128 caracteres, entonces el sistema deberá mostrar errores locales asociados a los campos sin enviar una petición. (→ F-01.AC1)
- **R3** (Por evento) Cuando se envíe un login de personal válido, el sistema deberá llamar una sola vez a `POST /api/v1/auth/login` con exactamente `{ email, password }`, sin Bearer ni tenant del cliente, manteniendo deshabilitado el envío mientras se resuelve y sin reintentos automáticos. (→ F-01.AC1, F-01.AC2)
- **R4** (Por evento) Cuando un login responda con un token vigente, el sistema deberá pedir `/api/v1/me` con Bearer explícito de ese token y guardar/activar sesión solo si la respuesta corresponde al acceso elegido: STAFF con rol reconocido para Personal, o PATIENT del tenant recordado para Paciente. (→ F-01.AC1, F-01.AC2, F-01.AC3, F-01.AC7)
- **R5** (No deseado) Si `/me` tiene un kind desconocido, rol STAFF desconocido, principal distinto del acceso elegido, tenant paciente distinto o datos requeridos incompatibles con el contrato, entonces el sistema deberá descartar el token del intento sin abrir contenido protegido y mostrar un error local de acceso. (→ F-01.AC2, F-01.AC3, F-01.AC4, F-01.AC7)
- **R6** (No deseado) Si el login responde 401, entonces el sistema deberá mostrar el mismo mensaje local de credenciales inválidas para cualquier cuerpo recibido, vaciar la contraseña, conservar el identificador escrito y no guardar sesión. (→ F-01.AC1)
- **R7** (No deseado) Si el login responde 429, entonces el sistema deberá mostrar el error local y bloquear nuevos envíos durante `Retry-After` si es un entero positivo, o 60 segundos en otro caso, sin reintentar automáticamente ni guardar sesión. (→ F-01.AC1)
- **R8** (No deseado) Si el login o su `/me` falla por red, 5xx u otro error no tratado, entonces el sistema deberá mostrar un mensaje de recursos de la app, conservar el identificador del formulario y no abrir contenido protegido ni guardar el token del intento fallido. (→ F-01.AC1, F-01.AC3)
- **R9** (Ubicuo) El sistema deberá mantener como máximo una sesión activa cuyo principal verificado y rol estén en memoria, guardar únicamente token cifrado con Keystore AES-256-GCM y expiración como sesión persistida, y conservar por separado la IPS/sede pública recordada del paciente sin persistir perfiles ni datos privados. (→ F-01.AC3, F-01.AC7; RNF-05, RNF-18)
- **R10** (Por evento) Cuando se restaure un token guardado vigente y descifrable, el sistema deberá verificarlo mediante `/me` antes de mostrar contenido protegido, permitiendo restaurar STAFF sin IPS paciente recordada y PATIENT únicamente con su tenant recordado coincidente. (→ F-01.AC2, F-01.AC3, F-01.AC7)
- **R11** (No deseado) Si la verificación de una sesión restaurada falla por red o 5xx, entonces el sistema deberá conservar su token cifrado pero mantener cerrado el contenido protegido y ofrecer Reintentar y Cerrar sesión con mensajes locales. (→ F-01.AC3, F-01.AC7)
- **R12** (No deseado) Si el token guardado está vencido, no puede descifrarse, tiene expiración inválida o la sesión activa alcanza su vencimiento, entonces el sistema deberá borrar la sesión y datos privados en memoria y volver al acceso sin abrir contenido protegido. (→ F-01.AC3, F-01.AC7)
- **R13** (Por evento) Cuando una petición protegida de la sesión vigente responda 401, el sistema deberá cerrar centralmente esa sesión y reiniciar navegación y datos privados, conservando la IPS/sede paciente recordada y sin llamar a un endpoint de logout. (→ F-01.AC3, F-01.AC7)
- **R14** (Por evento) Cuando el usuario confirme cerrar sesión o cambiar tipo de acceso, el sistema deberá borrar token/expiración, invalidar la generación anterior y destruir su navegación, consultas y borradores, de modo que Atrás no muestre pantallas de la sesión anterior. (→ F-01.AC3, F-01.AC7; plan móvil, sesión única)
- **R15** (No deseado) Si termina una petición o callback de un intento o sesión invalidado, entonces el sistema deberá descartarlo sin reabrir sesión, mostrar datos o errores anteriores, enviar una operación con el token de una sesión posterior ni cerrar esa sesión posterior por un 401 antiguo. (→ F-01.AC3, F-01.AC4, F-01.AC7)
- **R16** (Por estado) Mientras haya una sesión verificada, el sistema deberá dirigir al inicio de su principal/rol y mostrar únicamente los destinos permitidos de la matriz, con cierre de sesión, nombre/rol del personal en memoria y marcadores claramente pendientes para las funciones aún no implementadas. (→ F-01.AC2, F-01.AC3; plan móvil, destinos staff)
- **R17** (No deseado) Si se intenta abrir un destino cuyo principal o rol no está permitido, entonces el sistema deberá denegar su contenido sin ejecutar las peticiones de esa función, manteniendo acceso solo al inicio permitido o al login cuando no haya sesión verificada. (→ F-01.AC3, F-01.AC7)
- **R18** (Ubicuo) El sistema deberá añadir Bearer únicamente a rutas protegidas con el token de la generación que originó la operación, excluir `/public/` y `/auth/` y conservar Authorization explícita de `/me`, sin permitir que el principal paciente llame a endpoints del personal ni que STAFF monte las funciones privadas del paciente. (→ F-01.AC3, F-01.AC4, F-01.AC7)
- **R19** (Ubicuo) El sistema deberá conservar el comportamiento, permisos y pruebas de F-01-mobile y F-02-mobile para alta/consentimiento, perfil propio, preregistro y último estado, adaptando solo la integración de sesión/navegación de este bloque y manteniendo las APIs de patients/encounters limitadas a paciente/public. (→ F-01.AC7, F-01.AC8; F-02.AC8, F-02.AC10)
- **R20** (Ubicuo) El sistema deberá mantener identificadores personales, contraseñas, token, perfil y borradores solo en las ubicaciones autorizadas, enmascararlos en `toString`, excluirlos de logs y estado guardado, y presentar los errores mediante recursos locales sin mostrar `title`, `detail` ni `errors[].message` de la API. (→ F-01.AC1, F-01.AC7; RNF-05, RNF-18)
- **R21** (Ubicuo) El sistema deberá ofrecer entrada, login y destinos provisionales usables con teclado, etiquetas accesibles, desplazamiento y `WindowSizeClass` en teléfono y tablet, conservando formularios en ViewModel al rotar y descartándolos al cambiar sesión o morir el proceso. (→ F-01.AC1, F-01.AC7; RNF-13)

## Preguntas abiertas

Ninguna. Se usan los mínimos del plan aprobado: bienvenida sin sesión, acceso elegido en memoria, perfil únicamente en memoria, token cifrado único y ningún destino staff operativo antes de su bloque. Idiomas/temas, historial propio de solicitudes, recepción, clínica, dashboards y voz llegan en los bloques posteriores; F-02 existente no se reimplementa aquí.
